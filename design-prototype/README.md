# Secure Testing: интерактивный UI-прототип

Самостоятельный HTML/CSS/vanilla JS прототип по трем предоставленным PDF-экспортам Figma и документам PROJECT_SPEC_15.md / VKR_CONTEXT_15.md. Покрывает 24 кадра. Основание: `master` на коммите `177538b9a2cf86128b4726b0a44efacd0c2534cc`. Изменения находятся только в новом каталоге `design-prototype/`, в ветке `design/ui-prototype`.

**Это кликабельный макет с демонстрационными данными. Реальная авторизация, серверные операции и безопасность здесь не реализованы. Этапы 16-18 не выполнены. Django, существующая документация и backend не изменены.**

## Запуск

Из корня репозитория, после переключения на ветку `design/ui-prototype`:

```sh
python -m http.server 8000 --bind 127.0.0.1 --directory design-prototype
```

Открыть <http://127.0.0.1:8000/preview.html>. Требуется Python 3 только для раздачи статических файлов. Прототип не выполняет API-запросы, не использует CDN, npm или внешний backend. Inter включен локально с лицензией SIL OFL.

`preview.html` является отдельным служебным каталогом сценариев, а не пользовательским экраном приложения. На ней доступны роли, 24 кадра и сброс данных. Кнопка конкретного кадра загружает его исходную демонстрационную ситуацию и сбрасывает предыдущие изменения. Верхние ссылки ролей сохраняют изменения, поэтому можно закрыть тест преподавателем, затем продолжить ранее начатую попытку студентом.

Пользовательские экраны находятся в `app.html`. На них нет переключателя роли. Вход демонстрируется с `student1`, `teacher1`, `admin1` и единым публичным паролем `demo1234`. Созданные в макете учетные записи также используют этот демонстрационный пароль: значение поля создания пароля не сохраняется. Это не воспроизводит Django password validation или PBKDF2.

## Сценарии

- TEACHER: создание и редактирование черновика, вопросы/варианты/позиции, проверка готовности, подтверждение активации, назначения, чтение содержания и результатов, подтверждение закрытия. Обратных переходов и удаления нет.
- STUDENT: назначенные ACTIVE/CLOSED тесты, старт и продолжение своей попытки, сохранение и изменение ответа, переходы по вопросам, подтверждение завершения с пропусками, итоговые баллы и процент. Закрытие теста не завершает начатую попытку.
- ADMIN: список и создание пользователей, изменение роли другого пользователя, подтверждение блокировки/разблокировки, конфликт 409 при смене роли владельца ACTIVE теста, журнал только для чтения.
- Общие компоненты: поля, ошибки, статусы, disabled, кратковременный loading, уведомления, диалоги, клавиатурный фокус, нейтральные страницы 400/403/404/409.

Состояние хранится в `localStorage` под ключом `secure-testing-prototype-v1`, выбранный демонстрационный пользователь в `sessionStorage`. Пользуйтесь вымышленными данными. Весь набор данных, включая признаки правильных ответов, доступен в исходном JavaScript и хранилище браузера. Скрытие сведений в представлении STUDENT не является защитой передачи данных. Проверки ролей, принадлежности, lifecycle, лимитов и блокировки являются только поведением макета и обходятся через инструменты разработчика. Нет Django Sessions, CSRF, RBAC/API-защиты, защиты от перебора, транзакций, серверного журнала или гарантии конкурентной целостности. Журнал содержит синтетические события.

## Файлы

- `preview.html`, `preview.js`: каталог 24 кадров, выбор демонстрационной ситуации, сброс.
- `app.html`, `app.js`: семантические представления, формы, локальные данные и переходы.
- `styles.css`: общие компоненты, CSS custom properties, адаптация ширины.
- `assets/InterVariable.woff2`, `assets/Inter-LICENSE.txt`: локальный шрифт и лицензия.
- `SCREEN_AUDIT.md`: постраничная сверка с PDF и привязка к требованиям.
- `checks/browser-check.cjs`: воспроизводимые браузерные проверки прототипа.
- `qa/screen-01.png` ... `qa/screen-24.png`: снимки всех кадров при viewport 1440 x 900.
- `qa/results.json`: результат браузерного прогона.

## Выполненные проверки

```sh
node --check design-prototype/app.js
node --check design-prototype/preview.js
```

Обе команды завершились с кодом 0. Для браузерных проверок в среде разработки был запущен статический сервер:

```sh
python -m http.server 8765 --bind 127.0.0.1 --directory design-prototype
```

В отдельном терминале выполнено:

```sh
CHROMIUM_EXECUTABLE=/tmp/ui-browser/chrome-headless-shell-linux64/chrome-headless-shell node design-prototype/checks/browser-check.cjs
```

В проверочной среде Playwright доступен через `CODEX_PRIMARY_RUNTIME_NODE_MODULES`. Использован Chrome Headless Shell 134.0.6998.35. При наличии обычной локальной установки Playwright и ее Chromium достаточно `node design-prototype/checks/browser-check.cjs`; `CHROMIUM_EXECUTABLE` необязателен. `PROTOTYPE_URL` переопределяет адрес сервера, `QA_OUTPUT` каталог снимков (по умолчанию `/tmp/secure-testing-ui-qa`). Playwright нужен только разработчику для проверки, не для запуска макета.

Результат: PASS, 24 кадра; формы и переходы трех ролей; сохранение после обновления страницы; завершение с пропусками; продолжение после закрытия; конфликт роли; блокировка/разблокировка; нейтральный 404; буквальный вывод введенного HTML; вход/выход; отсутствие ошибок JavaScript и внешних запросов. На 390 x 844 проверены горизонтальный overflow и доступность фокуса клавишей Tab на списке студента. Это не полный аудит доступности, не проверка всех мобильных экранов и не security-тест backend.

Визуально сопоставлены все 24 снимка с соответствующими страницами PDF. Подробности и отличия: [SCREEN_AUDIT.md](SCREEN_AUDIT.md). Для утверждения: [вход](qa/screen-02.png), [DRAFT](qa/screen-05.png), [ACTIVE](qa/screen-10.png), [Attempt](qa/screen-15.png), [Result](qa/screen-17.png), [Users](qa/screen-19.png), [Audit](qa/screen-22.png).
