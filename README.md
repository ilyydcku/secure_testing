# Secure Testing

**Разработка и исследование защищенного веб-приложения для онлайн-тестирования**

Учебный проект ВКР: веб-приложение для создания и прохождения тестов с серверным разграничением прав, защитой данных и последующим исследованием безопасности.

> Состояние проекта: завершен этап 16 (функциональность преподавателя). Интерфейсы студента и администратора пока представлены в отдельном демонстрационном прототипе и не являются готовыми модулями Django.

## Назначение и роли

- **Преподаватель (TEACHER):** в реализованном Django-приложении создает и редактирует черновики тестов, вопросы и варианты ответов, активирует и закрывает тесты, назначает их студентам и просматривает итоговые результаты.
- **Студент (STUDENT):** в планируемой серверной реализации получает назначенные тесты, проходит попытки и просматривает собственные результаты. Соответствующие пользовательские экраны пока доступны в прототипе.
- **Администратор (ADMIN):** по проекту управляет учетными записями, ролями и блокировками, просматривает журнал событий. Полноценный рабочий интерфейс администратора еще не реализован.

Макет охватывает все три роли, но не заменяет серверную реализацию и не доказывает выполнение требований безопасности.

## Архитектура

Проект организован как модульный монолит Django с общей бизнес-логикой для Django Templates и Django REST Framework (DRF). Данные хранятся в PostgreSQL.

- `accounts/`: пользователи, серверная аутентификация, бизнес-роли и проверки доступа.
- `assessments/`: тесты, вопросы, варианты ответов, назначения, попытки и результаты; здесь же находится реализованный интерфейс преподавателя.
- `auditlog/`: модель и область доступа к событиям журнала; полноценное журналирование еще не завершено.
- `config/`: настройки Django и маршрутизация.
- `tests/`: автоматизированные проверки.
- `docs/`: техническая документация и исторические материалы.

В модели данных предусмотрены девять согласованных сущностей: User, Test, Question, AnswerOption, TestAssignment, Attempt, StudentAnswer, Result и AuditEvent.

## Безопасность и границы текущей реализации

В коде реализованы серверные Django Sessions и DRF SessionAuthentication, защита CSRF, проверки активной бизнес-роли, ограничение доступа к объектам и контролируемая выдача полей в API и шаблонах преподавателя. Операции изменения тестов на этапе 16 проверяют права и состояние в транзакциях.

Настроены ограничения сессий; режим `DJANGO_HTTPS=True` выставляет флаги Secure для session/CSRF cookies, но сам по себе не создает HTTPS-сервер. Защита от перебора, полноценное серверное журналирование и оставшиеся исследования безопасности относятся к последующим этапам. Наличие `django-axes` в зависимостях не означает, что этот механизм уже подключен.

Это учебная реализация, а не готовая production-система. Подтверждение отдельных проверок не означает завершение всех испытаний безопасности.

## Локальная установка и запуск (Windows PowerShell)

Необходимы Python 3.13 и PostgreSQL 18. Команды выполняются из корня репозитория.

1. Создать виртуальное окружение и установить зависимости:

```powershell
py -3.13 -m venv .venv
& ".\.venv\Scripts\python.exe" -m pip install -r requirements.txt
```

2. При первой настройке PostgreSQL создать локальную роль и базу. В интерактивном `psql` под администратором:

```sql
CREATE ROLE secure_testing WITH LOGIN;
\password secure_testing
CREATE DATABASE secure_testing OWNER secure_testing;
\q
```

3. Создать локальный файл окружения и заполнить его своими значениями `DJANGO_SECRET_KEY` и `POSTGRES_PASSWORD`:

```powershell
Copy-Item .env.example .env
notepad .env
```

Для локального HTTP оставить `DJANGO_HTTPS=False`; файл `.env` исключен из Git. Значение `DJANGO_SECRET_KEY` можно создать командой:

```powershell
& ".\.venv\Scripts\python.exe" -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
```

4. В каждом новом окне PowerShell загрузить переменные из `.env`:

```powershell
Get-Content .env | ForEach-Object {
    if ($_ -match '^([^#][^=]*)=(.*)$') {
        Set-Item -Path "Env:$($matches[1])" -Value $matches[2]
    }
}
```

5. Применить миграции, проверить проект и запустить локальный сервер:

```powershell
& ".\.venv\Scripts\python.exe" manage.py migrate
& ".\.venv\Scripts\python.exe" manage.py check
& ".\.venv\Scripts\python.exe" manage.py runserver 127.0.0.1:8000
```

Открыть `http://127.0.0.1:8000/login/`. Для просмотра реализованного кабинета нужна существующая **активная** учетная запись с ролью `TEACHER`; ее можно создать через предусмотренный сервис из `manage.py shell`. Учетные данные демонстрационного макета не подходят для настоящего приложения.

## Тестирование

После загрузки переменных `.env` из корня проекта:

```powershell
& ".\.venv\Scripts\python.exe" -m pytest -v --tb=short
& ".\.venv\Scripts\python.exe" manage.py check
& ".\.venv\Scripts\python.exe" manage.py makemigrations --check --dry-run
```

Браузерный тест запускается отдельно после установки Chromium для Playwright; точные команды и ограничения проверки приведены в [отчете этапа 16](docs/STAGE_16.md).
