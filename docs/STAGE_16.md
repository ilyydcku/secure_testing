## Что реализовано

- Общие транзакционные операции Test, Question, AnswerOption, TestAssignment.
- Все согласованные TEACHER API: тесты, вопросы, варианты, активные студенты,
  назначения, итоговые результаты.
- Django Templates/forms: список, создание/изменение черновика, редактор вопроса,
  активация, назначения, закрытие, чтение вопросов и результатов.
- HTML-вход и POST-выход через стандартную Django authentication и Sessions.
  Это необходимый вход в интерфейс преподавателя. API аутентификации этапа 13
  сохранен. Для остальных ролей пока доступно только сообщение об успешном входе;
  их рабочие интерфейсы остаются этапами 17 и 18.
- Цвета, сетка, компоненты и локальный Inter из согласованного макета.
  В рабочее приложение не перенесены фикстуры, демонстрационная авторизация,
  localStorage или клиентские проверки макета как механизм защиты.

Модели, миграции, зависимости, PostgreSQL-конфигурация, authentication API,
существующие сервисы User и тесты этапов 12-15 не изменены.

## Доступ и целостность

Роль проверяется до обращения к защищенному объекту. Существующий чужой объект
и отсутствующий объект дают нейтральный 404. Lifecycle-конфликты, повторные
назначения и занятые позиции дают 409. Лишние поля и неверные данные дают 400.
CSRF применяется ко всем unsafe-запросам через штатные механизмы Django/DRF.

Выдача API и контексты бизнес-данных шаблонов ограничены явными проекциями.
Список кандидатов содержит только id/username активных STUDENT. Результаты
содержат только id/student_id/score_points/correct_percentage, без ответов и
прямых объектов Attempt. DELETE и teacher API для Attempt/StudentAnswer нет.

Изменение теста и его содержания, назначения, активация и закрытие выполняются
в atomic-транзакции после блокировки Test и повторной проверки текущего доступа
и состояния. Активация сначала блокирует User-владельца, что согласовано с
существующим сервисом смены роли. При назначении после Test блокируется только
подходящий активный STUDENT и повторно проверяется его пригодность.

Закрытие запрещает новые попытки и назначения, но не изменяет существующие
Attempt/StudentAnswer/Result. Создание/завершение попыток остается этапом 17.

HTML-редактор сохраняет вопрос и явно переданный полный список его вариантов
одной транзакцией. Он позволяет изменить правильный вариант и поменять позиции
без частичного сохранения, сохраняет id существующих вариантов, не удаляет их.
Подмена id варианта, пропуск существующего варианта и повтор id отклоняются.
При перестановке позиций используются временные свободные положительные позиции
внутри той же транзакции, чтобы соблюдать немедленный UNIQUE БД.

API AnswerOption изменяет только адресованный вариант. Если другой вариант уже
правильный, попытка выставить второй is_correct=true возвращает 409. В API нужно
сначала снять прежний признак, затем установить новый. DRAFT может временно быть
не готов; активация требует ровно один правильный вариант и минимум два варианта
для каждого вопроса. HTML-форма выполняет такую смену атомарно.

Журналирование остается этапом 20; django-axes и дополнительное усиление защиты
не объявляются выполненными. UI не является доказательством серверной безопасности.

## Проверка в локальном окружении пользователя

В существующем PowerShell-окружении проекта с настроенными POSTGRES_* и
DJANGO_SECRET_KEY, после получения ветки stage16/teacher:

```powershell
& ".\.venv\Scripts\python.exe" -m pytest -v --tb=short
& ".\.venv\Scripts\python.exe" manage.py check
& ".\.venv\Scripts\python.exe" manage.py makemigrations --check --dry-run
```

При успешном полном запуске текущего набора на PostgreSQL ожидаются 420 passed
и один skip браузерного теста. Это ожидаемый результат, не результат уже
выполненного PostgreSQL-прогона.

Браузерная проверка не требует Node.js или npm:

```powershell
& ".\.venv\Scripts\python.exe" -m playwright install chromium
$env:RUN_BROWSER_TESTS = "1"
& ".\.venv\Scripts\python.exe" -m pytest tests/test_teacher_stage16_browser.py -v --tb=short
Remove-Item Env:RUN_BROWSER_TESTS
```

При необходимости CHROMIUM_EXECUTABLE указывает путь к установленному Chromium,
BROWSER_QA_OUTPUT задает каталог снимков. Тест использует отдельную тестовую БД,
а не пользовательские данные основной БД.

Для ручного просмотра: запустить manage.py runserver и открыть
http://127.0.0.1:8000/login/ под существующим TEACHER. Создание учетных записей
через административный интерфейс еще не подключено, это этап 18.

Этап 16 закрывается после успешного PostgreSQL-прогона и фиксации его результата.
